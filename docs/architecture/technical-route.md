# 技术路线与开发验收

以下路径均相对于仓库根目录。本地电脑负责编辑与资产管理，视频推理和小规模训练使用单独的 NVIDIA GPU 环境；具体配置在核实显存并完成输入兼容性验证后确定。以下是后续实现路线；已实现的工具以 [README](../../README.md) 为准，Windows 操作见 [交接文档](../../WINDOWS_HANDOFF.md)。

## 1. 角色协议

每个角色版本拥有 character_id、revision、parent_revision、拓扑与单位标识、neutral_mesh、shape_parameters、texture_assets、expression_model_version、编辑记录、参考渲染与内容哈希。修改产生新 revision，不覆盖原版。

编辑记录包含 semantic_region、signed_amount、unit、baseline_revision、canonical_vertex_delta、support_mask、transition_band。FLAME 系数与语义滑块之间需要单独的映射层，不直接让用户操作 PCA。前端 Three.js 与离线 Blender 使用相同拓扑、坐标、单位和表达模型版本，保存后重新加载必须得到相同顶点。

现阶段 schemas/character.example.json 仅是字段草案，不是验证完备的正式 schema，也不含可用人脸资产。

## 2. 控制数据

对同一 pose、expression、camera 分别动画化原版与编辑版网格。输出目标法线、深度、UV 对应、可见性、编辑区域与几何增量投影。驱动者只能提供表情、姿态，不能替换角色身份形状。

R1 的原生 ConsisID/FantasyID 只通过 prompt 请求动作，不能直接输入驱动视频或精确相机轨迹；生成后按姿态、表情分桶并记录动作完成率。固定轨迹或已有驱动视频仅用于新增逐帧几何分支后的独立条件集。验证增量时，使用同一个已具备完整几何与动作条件的基座，比较加入与不加入增量。不要把新增动作可控能力归因于增量。

## 3. 研究模块

主基座先选 ConsisID。模型入口：[transformer_consisid.py](https://github.com/PKU-YuanGroup/ConsisID/blob/main/models/transformer_consisid.py)、[pipeline_consisid.py](https://github.com/PKU-YuanGroup/ConsisID/blob/main/models/pipeline_consisid.py)、[train.py](https://github.com/PKU-YuanGroup/ConsisID/blob/main/train.py)。原有身份和外观路径保留，几何与增量通过新增残差模块注入；需要自行实现，不是修改一个参数即可完成。

顺序：先改后完整形状点云 token，再测试逐帧几何分支，最后加入局部增量及动态控制。每步保存同一底模 checkpoint 和配置哈希，报告新增参数、训练数据和计算量。增量实验另做等容量零增量/普通区域条件分支，以及改前改后几何直接拼接，防止把参数量或额外标签当作新机制收益。静态形状 token 与逐帧几何是不同模块，逐项比较，避免一次加入所有机制。

已有监督视频缺少配对编辑真值，因此第一阶段使用授权合成配对渲染，固定其余条件。训练目标先使用视频扩散目标加配对重建；几何/剂量辅助损失仅在可微且经过校准的测量路径可用时加入。不要直接把非可微的外部拟合器写成可反向训练的损失，也不每一步完整解码并运行重建器。可先将几何估计作为离线评测，再验证低频采样的可微辅助头。

身份相似度目标使用编辑后版本；非目标保留采用语义区域及允许影响带的几何与外观约束。表情自然性以动作完成和独立人工评价校验。

## 4. 云端服务

统一提交、查询、取消、取回结果协议，适配器分别对应研究推理程序与产品生成后端。任务保存角色 revision、输入资产哈希、prompt、driver_hash、seed、scheduler、分辨率、帧数、模型版本及输出。ComfyUI 只是其中一个后端，研究训练不绑定其界面。

首轮不购买机器、不后台下载权重、不自动启动付费训练。云服务确定后先做一次推理和一次最小反向试验，记录峰值显存、耗时与失败原因，再排批量队列。模型环境和本地编辑器环境分离。

Wan2.2 Animate 的 pose_video 与 face_video 是既有条件；FLAME 法线并不是可直接替换其任意输入的保证。接入需经过兼容性试验。备选 Stand-In + VACE 有公开 infer_with_vace.py，但完整训练仍需自行补齐。

## 5. 依赖里程碑

| 阶段 | 可交付内容 | 验收与下一步 |
| --- | --- | --- |
| R0 输入与量测 | 两个角色、鼻翼/下巴编辑、改前后渲染、评估器校准 | 编辑区域正确，未编辑部分误差可解释；已知渲染能测出变化，强表情零编辑不被判为换形 |
| R1 最小基线 | ConsisID、FantasyID 原生推理，固定配置和结果台账 | prompt 动作条件下同一编辑对可复现，事后按姿态/表情分桶；记录编辑丢失、身份漂移、动作不足等失败类型 |
| R2 单底模实验 | 完整几何分支、局部增量、动态控制及消融 | 至少在未见身份上观察可重复改善；若只训练角色有效，先查过拟合和域差 |
| R3 外部验证 | 新镜头、强表情、遮挡恢复、外部方法与盲评 | 指标和人工判断一致，计入检测失败，按角色统计置信区间 |
| P1 编辑器 | React/TypeScript/Three.js，资产保存、版本、预览 | 与离线渲染一致，可在同一角色版本间切换 |
| P2 生成工作台 | FastAPI、SQLite、云任务、评测展示 | 每段结果可追溯到角色版本与模型；异常片段可以人工重试 |

P1 可与 R1 并行做最小界面，但不要为等待算法结论搭建完整产品。自动修复放在评测可靠之后；修复前后必须重新检查编辑和动作，不把换脸修复默认视为正确。

## 6. 后续首个开发任务

建立 FLAME 2023 Open 或自有统一拓扑角色的本地渲染验证链：加载一个角色，单独修改鼻翼，导出正面与侧面，重载角色参数并核对顶点与哈希。先确定统一规范尺度，单目拟合的毫米深度不作为直接真值。通过后再连接 GPU 视频基线。模型和纹理的使用范围应与实际取得的授权匹配。
